## 2. 프로젝트 선정 배경

Flex-log는 젊은 세대의 소비 증가와 소비 기록 습관 부족 문제에서 출발한 금융 웹 애플리케이션이다.

최근 젊은 세대는 SNS, 온라인 쇼핑, 배달 서비스, 구독 서비스 등 다양한 소비 환경에 쉽게 노출되어 있다. 소비 기회는 많아졌지만, 정작 본인이 어떤 항목에 얼마를 소비하고 있는지 명확히 인식하지 못하는 경우가 많다.

또한 SNS를 통해 타인의 소비 생활을 쉽게 접하면서 소비 욕구가 자극되거나 상대적 박탈감을 느끼는 경우도 있다. 여기에 물가 상승까지 더해지면서 소비 관리의 필요성은 커지고 있지만, 기존 가계부 서비스는 입력 방식이 번거롭고 지속적으로 사용하기 어렵다는 한계가 있다.

따라서 본 프로젝트는 사용자가 자신의 소비를 쉽고 재미있게 기록하고, 기록된 소비 데이터를 바탕으로 소비 습관을 분석하여 개선방안을 제시하는 서비스를 목표로 한다.

---

## 3. 주제 선정 이유

회의에서는 금융 프로젝트의 방향을 정하기 위해 젊은 세대의 소비 문제를 브레인스토밍 방식으로 정리하였다.

도출된 문제는 다음과 같다.

* 젊은 세대의 소비가 많다.
* 경제적인 노하우나 금융 지식이 부족하다.
* 소비 습관이 무분별하게 형성되기 쉽다.
* 물가가 높아 체감 지출 부담이 크다.
* SNS로 인해 소비 생활이 촉진된다.
* SNS를 통해 상대적 박탈감을 느낄 수 있다.
* 본인이 한 달에 얼마를 쓰는지 정확히 모르는 경우가 많다.
* 소비를 꾸준히 기록하는 습관이 부족하다.

이러한 의견을 바탕으로 문제의 핵심을 다음과 같이 정리하였다.

> 단순히 소비가 많은 것이 문제가 아니라, 사용자가 자신의 소비를 인식하고 관리하는 습관이 부족한 것이 핵심 문제이다.

## 4. 회의 결과 도출

브레인스토밍 결과, Flex-log의 핵심 방향은 다음과 같이 정리하였다.

> 본인의 소비를 기록하고 분석하여 소비 습관 개선방안을 제시하는 금융 웹 애플리케이션

프로젝트의 중요 포인트는 다음 두 가지이다.

| 핵심 포인트     | 설명                                          |
| ---------- | ------------------------------------------- |
| 기록         | 사용자가 소비 내역을 쉽고 재미있게 남길 수 있도록 SNS 방식을 활용한다.  |
| 소비 습관 개선방안 | 기록된 소비 데이터를 분석하여 AI 또는 규칙 기반으로 개선 방향을 제안한다. |

Flex-log의 핵심 흐름은 다음과 같다.

```text
소비 기록 → 소비 분석 → 개선방안 제시
```

## 5. 서비스 핵심 방향

## 5.1 기록 기능

기존 가계부 서비스는 금액과 카테고리를 직접 입력하는 방식이 중심이기 때문에 사용자가 흥미를 느끼기 어렵고, 기록을 지속하기 어렵다는 한계가 있다.

Flex-log는 이를 보완하기 위해 SNS 방식의 소비 로그를 활용한다.

사용자는 이미지 또는 영상을 업로드하고, 소비 금액, 소비 카테고리, 간단한 텍스트를 함께 작성할 수 있다.

소비 로그는 모든 사용자에게 공개되는 것이 아니라 친구 관계인 사용자에게만 공개되도록 하여, 개인적인 소비 기록이 무분별하게 노출되지 않도록 한다.

---

## 5.2 소비 습관 개선방안

사용자가 작성한 소비 로그는 단순 기록으로 끝나지 않고 소비 습관 분석의 기준 데이터가 된다.

소비 금액, 카테고리, 작성 시간 등을 기반으로 월별 소비 금액과 카테고리별 소비 패턴을 분석하고, 이를 바탕으로 소비 습관 개선방안을 제공한다.

AI 분석 기능을 활용할 수 있다면 사용자 맞춤형 피드백을 제공하고, 구현 시간이 부족할 경우 규칙 기반 분석으로 대체한다.

## 6. 기대 효과

Flex-log를 통해 기대하는 효과는 다음과 같다.

* SNS 방식으로 젊은 세대가 재미있게 소비를 기록할 수 있다.
* 소비 기록에 대한 진입 장벽을 낮출 수 있다.
* 사용자의 자발적인 소비 기록 습관을 촉진할 수 있다.
* 소비 로그가 쌓이면서 사용자의 소비 데이터를 확보할 수 있다.
* 사용자는 자신의 월별 소비와 카테고리별 소비 패턴을 확인할 수 있다.
* 분석 결과를 기반으로 소비 습관 개선방안을 제안받을 수 있다.
* 장기적으로 사용자가 자신의 소비를 인식하고 관리하는 습관을 형성할 수 있다.

# 7. 데이터 구조 설계

Flex-log의 데이터 구조는 소비 로그를 중심으로 설계한다.

사용자는 소비 로그를 작성하고, 작성된 소비 로그는 카테고리, 좋아요, 댓글, 친구 관계, 소비 분석 기능과 연결된다.

초기 데이터 구조는 다음 테이블을 중심으로 설계한다.

```text
User
Profile
Friend
Category
ExpenseLog
Like
Comment
MonthlyAnalysis
Feedback
```

향후 확장 기능으로는 다음 테이블을 고려한다.

```text
StockHolding
FinancialProduct
AIAnalysisLog
```

| AI 분석/피드백 | Feedback 또는 AIAnalysisLog 테이블 |
| 보유 주식 현황  | StockHolding 테이블              |

## 7.4 Friend 테이블

사용자 간 친구 관계를 저장하는 테이블이다.

Flex-log에서는 일반적인 팔로우/팔로워 구조가 아니라, 친구 요청을 보내고 상대방이 수락하면 서로 친구가 되는 구조를 고려한다.

이는 싸이월드의 일촌 개념과 유사하다.

| 필드         | 설명            |
| ---------- | ------------- |
| id         | 친구 관계 ID      |
| user_id    | 친구 요청을 보낸 사용자 |
| friend_id  | 친구 요청을 받은 사용자 |
| status     | 요청 상태         |
| created_at | 생성 시간         |
| updated_at | 수정 시간         |

status 값은 다음과 같이 관리한다.

| 값        | 설명       |
| -------- | -------- |
| pending  | 친구 요청 대기 |
| accepted | 친구 요청 수락 |
| rejected | 친구 요청 거절 |

친구 관계 설계 시 다음 규칙을 적용한다.

```text
두 사용자 사이에는 하나의 친구 관계만 존재한다.
친구 요청이 수락되면 양방향 친구 관계로 간주한다.
친구 관계가 accepted 상태인 사용자만 서로의 소비 로그를 볼 수 있다.
```

## 7.6 ExpenseLog 테이블

사용자가 업로드한 소비 로그를 저장하는 테이블이다.

기존 회의에서는 ConsumptionLog라는 이름도 고려하였으나, 실제 지출 기록이라는 의미가 더 명확한 ExpenseLog라는 이름을 사용하는 방향으로 정리하였다.

| 필드          | 설명          |
| ----------- | ----------- |
| id          | 소비 로그 ID    |
| user_id     | 작성자 ID      |
| category_id | 소비 카테고리 ID  |
| media       | 이미지 또는 동영상  |
| amount      | 소비 금액       |
| content     | 소비 로그 텍스트   |
| created_at  | 생성 시간       |
| updated_at  | 수정 시간       |
| expires_at  | 피드 노출 만료 시간 |
| is_visible  | 현재 피드 노출 여부 |

소비 로그는 친구 관계인 사용자만 볼 수 있도록 한다.

초기 아이디어에서는 로그 작성 후 24시간이 지나면 해당 로그를 삭제하는 방향을 고려하였다. 하지만 소비 로그가 실제로 삭제되면 월별 소비 분석과 카테고리별 소비 분석에 필요한 데이터가 사라지는 문제가 있다.

따라서 다음과 같이 수정한다.

```text
소비 로그는 24시간 후 피드에서만 보이지 않게 처리한다.
DB에서는 삭제하지 않고 소비 분석용 데이터로 유지한다.
```

즉, 24시간이 지나면 `is_visible` 값을 변경하거나 `expires_at` 기준으로 피드 노출 여부를 판단한다.

이렇게 하면 SNS 스토리처럼 24시간 뒤 사라지는 경험을 제공하면서도, 소비 분석 데이터는 유지할 수 있다.

## 7.7 Like 테이블

소비 로그에 대한 좋아요 정보를 저장하는 테이블이다.

| 필드         | 설명           |
| ---------- | ------------ |
| id         | 좋아요 ID       |
| user_id    | 좋아요를 누른 사용자  |
| log_id     | 좋아요 대상 소비 로그 |
| created_at | 생성 시간        |

좋아요 기능에서는 다음 규칙을 적용한다.

```text
한 사용자는 하나의 소비 로그에 한 번만 좋아요를 누를 수 있다.
```

이를 위해 `user_id`와 `log_id`의 조합이 중복되지 않도록 관리한다.

---

## 7.8 Comment 테이블

소비 로그에 작성된 댓글 정보를 저장하는 테이블이다.

| 필드         | 설명          |
| ---------- | ----------- |
| id         | 댓글 ID       |
| user_id    | 댓글 작성자      |
| log_id     | 댓글 대상 소비 로그 |
| content    | 댓글 내용       |
| created_at | 생성 시간       |
| updated_at | 수정 시간       |

회의 초안에서는 댓글 테이블에 댓글 내용 필드가 빠져 있었으므로, 실제 설계에서는 `content` 필드를 추가한다.

## 7.9 MonthlyAnalysis 테이블

사용자의 월별 소비 분석 결과를 저장하거나 조회하기 위한 테이블이다.

| 필드               | 설명          |
| ---------------- | ----------- |
| id               | 분석 ID       |
| user_id          | 사용자 ID      |
| year             | 분석 연도       |
| month            | 분석 월        |
| total_amount     | 월별 총 소비 금액  |
| category_summary | 카테고리별 소비 요약 |
| created_at       | 생성 시간       |

해당 테이블은 반드시 처음부터 저장 테이블로 구현하지 않아도 된다.

초기에는 ExpenseLog 데이터를 조회하여 월별 소비 금액과 카테고리별 소비 금액을 계산하는 방식으로 구현하고, 필요하면 이후 분석 결과 저장 테이블로 확장한다.

## 7.10 Feedback 테이블

소비 분석 결과를 바탕으로 제공하는 개선방안을 저장하는 테이블이다.

| 필드            | 설명      |
| ------------- | ------- |
| id            | 피드백 ID  |
| user_id       | 사용자 ID  |
| analysis_id   | 분석 ID   |
| content       | 개선방안 내용 |
| feedback_type | 피드백 유형  |
| created_at    | 생성 시간   |

AI 분석 기능을 실제로 사용하기 어려운 경우, 초기에는 규칙 기반 피드백으로 구현한다.

예시는 다음과 같다.

```text
식비 비중이 전체 소비의 40% 이상이면 식비 절약 피드백 제공
카페 소비 횟수가 일정 기준 이상이면 카페 소비 조절 피드백 제공
쇼핑 소비가 전월 대비 증가하면 충동구매 주의 피드백 제공
```

| 2순위  | 소비 로그 | 소비 로그 조회 / 수정 / 삭제  |
| 3순위  | 친구    | 친구 요청 / 수락 구조 설계    |
| 4순위  | 좋아요   | 소비 로그 좋아요           |
| 4순위  | 댓글    | 소비 로그 댓글            |

이번 주 구현 범위에서는 이미지 업로드를 우선 구현하고, 동영상 업로드는 시간 여유가 있을 경우 추가한다.

```text
이번 주 우선 구현: 이미지 업로드
추가 구현 후보: 동영상 업로드
```

# 9. 브랜치 전략 논의

## 9.1 브랜치 전략 도입 배경

Flex-log는 2명이 2주 동안 진행하는 프로젝트이다.

짧은 기간 안에 기획, 설계, 백엔드, 프론트엔드, 문서화 작업을 동시에 진행해야 하므로 Git을 활용한 명확한 형상관리 전략이 필요하다.

특히 소비 기록, 소비 분석, 개선방안 제시 기능은 백엔드 API와 프론트엔드 화면이 밀접하게 연결되어 있기 때문에, 각자 작업한 코드가 충돌하거나 서로의 작업을 덮어쓰는 상황을 방지해야 한다.

따라서 회의에서는 Git 브랜치 전략을 함께 논의하였다.

---

## 9.2 참고 자료

브랜치 전략은 SSAFY 멘토 칼럼에서 좋은길벗 닉네임의 멘토님이 작성한 Git을 활용한 형상관리 사례를 참고하였다.

해당 사례는 팀 프로젝트에서 브랜치를 분리하여 작업하고, Pull Request를 통해 변경사항을 검토한 뒤 통합하는 방식의 중요성을 보여준다.

Flex-log 프로젝트는 2인 2주 프로젝트이므로, 해당 사례를 그대로 적용하기보다는 프로젝트 규모에 맞게 단순화하여 적용하기로 하였다.

---

## 9.3 브랜치 구조

Flex-log 프로젝트에서는 다음 브랜치를 사용한다.

```text
master
project/week1
project/week2
feature/작업내용-githubID
docs/문서명-githubID
fix/수정내용-githubID
```

전체 흐름은 다음과 같다.

```text
master
  ├── project/week1
  │     ├── feature/*
  │     ├── docs/*
  │     └── fix/*
  │
  └── project/week2
        ├── feature/*
        ├── docs/*
        └── fix/*
```

---

## 9.4 브랜치별 역할

| 브랜치           | 역할            |
| ------------- | ------------- |
| master        | 최종 안정 버전 관리   |
| project/week1 | 1주차 작업 통합 브랜치 |
| project/week2 | 2주차 작업 통합 브랜치 |
| feature/*     | 개인 기능 작업 브랜치  |
| docs/*        | 문서 작업 브랜치     |
| fix/*         | 버그 수정 브랜치     |

---

## 9.5 브랜치 운영 규칙

회의에서 정리한 브랜치 운영 규칙은 다음과 같다.

```text
1. master 브랜치에는 직접 push하지 않는다.
2. project/week 브랜치는 master에서 생성한다.
3. feature, docs, fix 브랜치는 project/week 브랜치에서 생성한다.
4. 작업 완료 후 Pull Request를 통해 project/week 브랜치로 병합한다.
5. PR 전 project/week 최신 코드를 본인 브랜치에 반영한다.
6. merge 완료된 작업 브랜치는 삭제한다.
7. 코드뿐 아니라 문서도 Git으로 관리한다.
```

---

## 9.6 브랜치 생성 예시

1주차 통합 브랜치는 다음과 같이 생성한다.

```bash
git switch master
git pull origin master

git switch -c project/week1
git push -u origin project/week1
```

개인 기능 작업 브랜치는 다음과 같이 생성한다.

```bash
git switch project/week1
git pull origin project/week1

git switch -c feature/backend-expense-jmkim
```

문서 작업 브랜치는 다음과 같이 생성한다.

```bash
git switch project/week1
git pull origin project/week1

git switch -c docs/project-meeting-jmkim
```

---

## 9.7 Pull Request 흐름

작업 브랜치에서 기능 또는 문서 작업을 완료하면 GitHub에 브랜치를 push한 뒤 Pull Request를 생성한다.

```bash
git add .
git commit -m "docs: 초기 기획 회의록 작성"
git push -u origin docs/project-meeting-jmkim
```

Pull Request 방향은 다음과 같다.

```text
feature/작업브랜치 → project/week1
docs/문서브랜치 → project/week1
fix/수정브랜치 → project/week1
```

2주차 작업은 `project/week2`를 대상으로 Pull Request를 생성한다.

```text
feature/작업브랜치 → project/week2
docs/문서브랜치 → project/week2
fix/수정브랜치 → project/week2
```

---

## 9.8 충돌 발생 시 해결 방식

Pull Request 전에는 최신 `project/week` 브랜치의 내용을 본인 작업 브랜치에 반영한다.

```bash
git switch feature/backend-expense-jmkim
git fetch origin
git merge origin/project/week1
```

충돌이 발생하면 충돌 파일을 직접 수정한 뒤 다시 커밋하고 push한다.

```bash
git add .
git commit -m "fix: project/week1 병합 충돌 해결"
git push
```

병합 과정이 너무 꼬였을 경우 다음 명령어로 병합을 취소할 수 있다.

```bash
git merge --abort
```

---

## 9.9 merge 후 브랜치 삭제

Pull Request가 승인되고 GitHub에서 merge가 완료되면 작업 브랜치는 삭제한다.

GitHub에서 원격 브랜치를 삭제한 뒤, 로컬에서도 다음과 같이 삭제한다.

```bash
git switch project/week1
git pull origin project/week1

git branch -d feature/backend-expense-jmkim
```

문서 브랜치라면 다음과 같이 삭제한다.

```bash
git branch -d docs/project-meeting-jmkim
```

# 14. 회의 요약

이번 회의에서는 Flex-log의 프로젝트 선정 배경, 핵심 기능 방향, 데이터 구조, 브랜치 전략, 이번 주 개발 목표를 정리하였다.

Flex-log는 젊은 세대의 소비 기록 습관 부족과 소비 인식 부족 문제를 해결하기 위해 기획되었다.

서비스의 핵심은 SNS 방식으로 소비를 재미있게 기록하고, 기록된 소비 데이터를 분석하여 소비 습관 개선방안을 제시하는 것이다.

데이터 구조는 User, Profile, Friend, Category, ExpenseLog, Like, Comment를 중심으로 설계하고, 분석 기능은 MonthlyAnalysis와 Feedback 구조로 확장하는 방향을 고려하였다.

또한 협업 과정에서 발생할 수 있는 충돌을 줄이기 위해 SSAFY 멘토 칼럼의 Git 형상관리 사례를 참고하여 master, project/week, feature, docs, fix 브랜치 전략을 적용하기로 하였다.

이번 주에는 Django 백엔드를 중심으로 회원가입, 로그인, 프로필, 소비 로그, 카테고리 기능을 우선 구현하고, 이후 친구 관계, 좋아요, 댓글 기능을 순차적으로 구현하는 것을 목표로 한다.

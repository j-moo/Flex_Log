# 06. 회고

## 프로젝트 결과 요약

Flex Log는 소비 기록, 친구 피드, 월별 분석, 금융 상품 추천, 주식 보유 현황을 하나의 서비스 흐름으로 연결했습니다. 기능 수가 많기 때문에 단순 CRUD 완성보다 사용자별 데이터 격리, 공개 범위, 외부 API 실패 대응, 프론트엔드 저장소 정책이 전체 품질을 좌우했습니다.

현재 코드는 다음 구조를 갖습니다.

- 백엔드: Django 앱 7개(`accounts`, `profiles`, `friends`, `expenses`, `analysis`, `finance`, `notifications`)
- 프론트엔드: Vue route 기반 화면 20개 이상
- 외부 API: GMS, FinLife, Kiwoom, YouTube, Kakao
- 저장 데이터: 사용자, 프로필, 친구, 소비 로그, 월별 분석, 금융 상품, 추천, 원자재, 주식, 알림

## 잘된 점

### 도메인 분리

앱이 기능별로 나뉘어 있어 수정 범위를 추적하기 쉽습니다. 예를 들어 소비 로그의 공개 범위 문제는 `expenses.views.accessible_log_queryset()`과 serializer 정책을 중심으로 확인할 수 있고, 금융 상품 필터 문제는 `finance.views.apply_product_filters()`에서 확인할 수 있습니다.

### 사용자별 데이터 소유권

대부분의 조회 API가 `request.user`를 기준으로 데이터를 필터링합니다. 소비 로그, 월별 분석, 금융 상품 가입, 주식 보유, 알림이 모두 사용자별로 분리되어 있습니다.

### 공개 범위 정책 개선

소비 로그는 공개 범위가 복잡합니다. 현재 코드는 다음 요소를 함께 고려합니다.

- 작성자 본인 여부
- accepted 친구 관계
- `visibility`: `public`, `friends`, `private`
- `is_visible`
- `expires_at`
- `hide_amount`

특히 피드와 타인 조회에서는 만료된 로그를 제외하고, 본인 목록은 기록 보존 목적으로 만료 여부를 적용하지 않는 점이 명확해졌습니다.

### 개인정보 노출 방어

프로필 응답에서 이메일은 본인에게만 노출됩니다. 친구 검색에서도 이메일을 검색하지 않으므로, 이메일 주소 유추 가능성이 줄었습니다.

### 프론트엔드 상태 분리

월 수입은 분석의 위험도 계산에 영향을 주는 값입니다. 브라우저 localStorage에 단일 key로 저장하면 같은 기기에서 다른 계정이 이전 계정의 월 수입을 재사용할 수 있습니다. 현재는 `flexlog.monthlyIncome.<userId>` 형식으로 분리되어 계정 간 값이 섞이지 않습니다.

### 주식 차트 안정화

보유 종목을 추가한 뒤 그래프가 나타나지 않는 문제는 차트 인스턴스 생성 시점과 데이터 로딩 상태가 어긋난 것이 원인이었습니다. 종목 변경과 로딩 완료 시 차트를 재생성하도록 수정해 새 종목 추가 후에도 차트가 표시됩니다.

## 코드 리뷰로 확인한 주요 리스크

### 1. 일부 한글 문자열 인코딩 깨짐

백엔드 모델 choices, validation message, notification message, 일부 프론트 mock 데이터에 깨진 한글 문자열이 남아 있습니다. 기능 자체는 동작할 수 있지만, 사용자에게 그대로 노출되면 품질 문제가 됩니다.

영향 파일 예:

- `backend/friends/models.py`
- `backend/expenses/models.py`
- `backend/expenses/views.py`
- `backend/analysis/views.py`
- `backend/finance/models.py`
- `backend/finance/views.py`
- `backend/notifications/models.py`
- `frontend/src/api/finance.js`

개선 방향:

- 모든 사용자 표시 문자열을 UTF-8 한글로 복구합니다.
- 테스트에서 대표 오류 메시지와 notification title/message를 확인합니다.
- 깨진 문자열을 검색하는 CI 체크를 추가합니다.

### 2. 외부 API 장애 경계

GMS, Kiwoom, YouTube, Kakao는 모두 외부 장애 가능성이 있습니다. 일부 기능은 fallback이 있지만, 기능마다 사용자 안내 수준이 다릅니다.

개선 방향:

- 외부 API별 timeout, 오류 메시지, logging 형식을 통일합니다.
- 프론트엔드 빈 상태와 오류 상태 UI를 일관되게 만듭니다.
- 운영 환경에서는 외부 API 장애율과 지연 시간을 모니터링합니다.

### 3. 페이지네이션 정책 불균형

피드는 `limit`/`offset`을 지원하지만, 상품 목록, 추천 이력, 알림 목록은 각각 별도 방식으로 처리됩니다. 알림은 최신 80개 제한이 있고, 상품 목록은 전체 반환입니다.

개선 방향:

- DRF pagination 설정을 공통으로 도입합니다.
- 프론트엔드 목록 화면도 page/limit 또는 cursor 기준으로 맞춥니다.

### 4. 운영 저장소 미분리

개발 환경은 SQLite와 로컬 `MEDIA_ROOT`를 사용합니다. 운영 환경에서는 동시성, 백업, 파일 저장 안정성을 위해 별도 DB와 오브젝트 스토리지가 필요합니다.

개선 방향:

- PostgreSQL 등 운영 DB 설정 분리
- 미디어 파일을 S3 호환 저장소로 이동
- 정적 파일 배포 전략 수립

### 5. 금융 추천 근거 설명

추천 결과는 분석과 상품 옵션을 연결하지만, 사용자 입장에서 “왜 이 상품인지”를 더 검증 가능하게 보여줄 여지가 있습니다.

개선 방향:

- 추천 사유에 월 소비 총액, 주요 카테고리, 기간, 최고 금리 등 근거 필드를 더 명확히 표시합니다.
- 추천 결과에 “금융 자문이 아닌 참고 정보”임을 UI에 명시합니다.

## 기능별 배운 점

### 인증

JWT는 구현이 간단하지만 저장 위치와 갱신 로직이 중요합니다. 현재 프론트엔드는 sessionStorage를 사용해 브라우저 세션 범위로 제한하고, refresh 요청 자체에는 retry loop가 걸리지 않도록 분기합니다.

### 소비 로그

소비 로그는 사용자 경험상 피드처럼 보이지만, 데이터 성격은 민감한 개인 금융 기록입니다. 따라서 공개 범위는 프론트엔드 표시만 믿지 않고 백엔드 queryset에서 최종 판정해야 합니다.

### 월별 분석

월 수입은 개인 설정이지만 현재 DB 모델에는 저장하지 않습니다. 이 선택은 구현을 단순하게 하지만, 여러 기기 간 동기화가 되지 않는 한계가 있습니다. 향후 사용자 설정 모델을 만들면 서버 저장으로 옮길 수 있습니다.

### 금융 상품

상품 기본 정보와 옵션을 분리한 설계는 적절했습니다. 예금/적금 상품 하나에 여러 기간과 금리 조건이 붙기 때문에 `FinancialProduct`와 `FinancialProductOption`의 1:N 구조가 자연스럽습니다.

### 주식

같은 종목을 다시 추가할 때 row를 중복 생성하지 않고 수량과 평균 단가를 재계산하는 정책은 사용자 경험상 직관적입니다. 다만 수량 serializer는 현재 정수 입력을 받으므로, 소수점 주식까지 지원하려면 serializer 타입을 모델과 맞춰 재검토해야 합니다.

## 검증 결과 기록 기준

기능 변경 PR에서는 최소 아래 결과를 남겨야 합니다.

```powershell
cd backend
python manage.py test
```

```powershell
cd frontend
npm run build
```

운영 배포 전에는 다음도 확인합니다.

```powershell
cd backend
python manage.py check --deploy
```

## 결론

Flex Log의 핵심은 기능 수보다 데이터 경계입니다. 소비와 금융 데이터는 민감하므로 사용자별 소유권, 공개 범위, 개인정보 노출 제한을 계속 우선순위에 둬야 합니다. 현재 구조는 기능 확장을 감당할 수 있는 기본 형태를 갖췄지만, 운영 품질로 가려면 인코딩 정리, 외부 API 관측성, pagination, 저장소 분리가 다음 단계입니다.
